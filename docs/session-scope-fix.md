# 会话数量异常：诊断与修复

日期：2026-10-28。当前契约：源库有对应消息表的会话与本地归档取并集，再排除隐藏项。完整通讯录不是会话名单，也不代表真实好友关系。

## 现象与入口

用户报告以前已归档约四百多个对象，更新全部也处理同量级对象，更新后出现一万多个待导入，多数归为好友。根目录 `启动微信聊天档案.cmd` 优先启动 `dist/微信聊天档案 完整语音版/app/desktop.py`，使用随包解释器和工作区 local_data；没有完整语音版时使用基础版。源码、运行副本、ZIP 分别更新。

## 两个独立问题

列表问题：`prepare_directory()` 将 `load_contacts(only_with_msg=False)` 的完整通讯录存入 contact_directory；旧 `directory_contacts()` 将全部目录与 chats 合并，所有没有归档的目录项被标为待导入。`classify_username()` 按编号特征分类，其他编号兜底为 friend，没有核验好友关系。不能从这个标签推断真实好友数，也不需要识别好友关系才能修复会话范围。

更新回归：836fd07 的 Manager.perform 对 update_all 向 Archive.update 传 usernames=None。导入层先按 Msg_ 表筛会话，补充 Name2Id 映射及已归档历史，最后排除隐藏。21cd072 的 U2 为预览与固定重试范围新增 maintenance_contacts，由完整目录起步；submit 固定显式名单，perform 改为 usernames=usernames。导入层 selected 非空语义为明确指定，会覆盖前面的筛选结果。因此完整通讯录绕过了消息表筛选。问题在范围定义，而非任务固定、预览或重试本身。

本会话早期只读重放曾得到旧范围438、新范围17876，额外17438项均无消息表，其中16188项被归为好友。它证明该份档案上的更新范围回归；数量仅为采样时状态，不作固定业务常数。修复后同一只读重放旧范围、当前范围与显式执行选择阶段均为438，额外对象0。439条归档元数据与438个可见对象属于隐藏过滤前后的不同集合。

列表扩张不能仅凭更新回归推断发生时间：旧版列表代码已合并完整通讯录；10月25日历史只读界面验收的原始浏览器结果记录“共17860个会话”，性能报告亦记录完整全选与滚动。证据证明当时验收把该异常规模用于性能和虚拟列表验证，没有核验这些对象是否为真实会话。无法证明用户昨天实际所见列表为何只有约439项，也无法据此否定用户观察；历史界面范围、运行状态等缺少直接记录，保留为未知。

## 为何原验证未发现

U2合成数据主要为每个目录项创建消息表，完整目录与会话集合接近，未模拟大量仅通讯录项。原测试还把没有消息表的本人、发送者等目录项算入待导入，断言324对象及参数传递，却未与改动前实际对象集合比较。性能验收确认能处理万项、滚动及全选，不能证明名单业务正确。这些结论分别来自 tests/u2_synthetic.py、test_u2.py、test_selective_import.py 和历史性能验收；没有证据支持对个人操作或动机作归责。

## 修复

Archive.directory_contacts 在读取时以源库消息表及通讯录/Name2Id映射建立会话集合，补充已有 chats；完整目录仅提供名称，不会自动成为会话。maintenance_contacts直接复用该实现。列表、项目有效范围、待导入、预览、任务提交校验因而一致。历史大目录保持原样，无需迁移或写真实账号；聊天、转写、关注、项目和隐藏配置均不清理。

隐藏管理保留隐藏对象的目录信息，即使其源表消失并已清理档案仍可管理。恢复后按同一日常范围判断是否可见。有源表的清理对象恢复后为待导入，保留档案的恢复后可读。搜索仍可用完整通讯录名称关联已收录发送者，不将匹配联系人自动加入会话列表。

加密账号“准备通讯录”现在准备消息实体分片，以便首次使用就具备会话表目录；不导入消息正文，不准备语音媒体。已有完整消息快照直接用于读取范围；源不可用时已有本地归档仍可列出。对象冻结、显式重试和事务发布保持原实现。
