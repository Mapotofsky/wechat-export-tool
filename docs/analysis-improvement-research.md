连续时间片段不是语义主题；字面提及变化不是观点变化。当前没有关键节点数据模型、线下背景管理窗口、语义索引、事件抽取或大模型摘要／问答。

当前性能证据仅限已验范围：11,352条真实消息、110,142项候选，完整分析约7–9秒；独立分析进程峰值约350–380MiB。单会话测量不代表全库，详见性能报告。

### 1.2 三阶段交付表

| 阶段 | 主要问题 | 交付内容 | 当前状态 |
|---|---|---|---|
| 第一阶段：字面证据与人工事实基础 | 找到原文；补充聊天以外的信息；人工整理重要事件 | 1A现有词句、比较、关联、证据流程；1B独立背景窗口、人工节点、可解释规则候选及统一时间线 | **1A已完成；1B新增规划，未实现** |
| 第二阶段：相似内容检索与节点召回 | 同一事项换种说法后仍能找到证据 | 可选本地嵌入、相似讨论、跨说法的节点证据候选；背景作为可选择的独立来源 | **规划，未实现** |
| 第三阶段：事件识别与有据归纳 | 谁在何时做了什么；进度或交往情况怎样变化 | 结构化节点抽取、事项进展、交往事件整理、带引用摘要与问答；候选确认及修订 | **规划，未实现** |

三阶段描述能力与开发顺序，不等同于基础版／完整语音版的发行包划分。第一阶段不增加内容模型下载、GPU要求或聊天上传。第二、三阶段模型按需启用，基础能力独立可用；本轮规划默认本地处理，在线文字模型接入不列入本轮交付项，也不沿用语音API的授权或配置。

### 1.3 两个新增功能放在哪里

**线下背景管理窗口放在第一阶段1B。** 它首先是本地结构化录入与阅读功能，不依赖模型，也是后续解释时间线和识别节点的输入基础。不能为了等模型选型而延迟背景管理。

**关键节点识别跨阶段递进，但完整语义识别属于第三阶段。**

- 第一阶段：用户直接记录／从原文标记节点；规则只找包含明确日期、事件或状态表达的候选位置，由用户确认事件含义。
- 第二阶段：用节点描述或用户选定证据召回其他说法，补足相关记录；相似度不代表事件成立或状态已经变化。
- 第三阶段：模型结合顺序、语境及用户选择的背景，抽取事件、时间、参与者和状态，区分提议、承诺、完成、撤回及解释；形成可编辑、带证据的候选节点。

这样既能尽早交付可用事件时间线，也不会将“命中交付”“聊天减少”直接解释成项目完成或关系疏远。

## 2. 全阶段共用业务契约

### 2.1 四种记录各有含义

| 对象 | 含义 | 谁可以改变 |
|---|---|---|
| 聊天原文 | 已导入文本及可用成功转写，保留发送者与稳定消息ID | 沿用现有归档／转写链路；分析不改写 |
| 背景记录 | 用户补充的线下经历、情况、计划或个人判断 | 用户显式新建、编辑、删除 |
| 节点 | 在某个事项或交往分析中值得保存的事件／状态表述，引用聊天或背景 | 用户创建或确认；机器只能提出候选 |
| 派生结果 | 规则／语义候选、摘要、相似结果及索引 | 可以重算，但不能覆盖用户已确认的内容 |

背景记录不伪装成聊天消息，不制造发送者和消息ID，不计入聊天总数、文本分母、词句频次及两期聊天提及比例。将来如统计背景或节点数量，必须单独命名和计数。

一条背景可以有零个或多个节点，一节点可以引用多条聊天／背景。一般背景说明无需强行转换成事件。人物称谓不自动对应联系人；显示名相同不能合并主体。

### 2.2 范围与来源

每次分析固定 `account_id`、会话／项目成员快照、日期、查询和成功转写条件。普通正文查询仍是字面约束；未来语义问题使用独立字段，不能把现有 `q` 静默改成语义检索。

背景可绑定会话、现有项目或保持未绑定。按当前范围读取背景时：

- 默认只展示直接绑定所选会话／所选项目的记录；未绑定、账号通用记录按需展开选择。
- 项目名称和成员变化不重写历史节点证据；本次分析展示实际成员快照。
- 时间已知的背景按事件时间与查询时间交集筛选；时间未知的记录单列并明确标记。
- 用户选定“分析背景集”后固定记录ID和修订号；模型只读这份明确集合，不默认读取账号全部笔记。
- 证据上下文可以按现有入口查看，但不增加查询命中数；扩大识别日期或会话范围必须显式应用并显示新范围。

### 2.3 日期、修订与原文定位

统一区分三个时间：消息发送时间、事件发生／计划时间、背景录入时间。晚录入的回忆不能因创建日期被排成新发生事件。

事件时间保存原始文字、起止值、精度（时刻／日／月／区间／未知）及解析依据。“大概六月”“明天”“下周可能”不能被强行压成一个确定时刻；相对时间以对应消息时间或用户明确指定的参考日解释。只知月份的事件按区间显示，区间交叠时不推断严格先后。

消息证据引用 `username + message_key`，保存所引文字摘录和字符跨度以便与当前正文核对；背景证据引用 `record_id + revision`。查看时检查引用是否仍可解析、文字是否已更新，不能悄悄把旧引用定位到另一段文字。无文字的消息只提供媒体位置，不能被当作文字陈述的支持证据。

## 3. 第一阶段：已交付基础与新增1B

### 3.1 1A完成状态

第1.1节能力已经完成，验收与性能修复已有独立记录。本轮不再把“添加词句筛选、两期比较、关联、旁侧原文”写成待开发任务，也不恢复以下旧假设：功能词天然无价值、否定表达额外优先、默认按月TF-IDF解释重点、片段置于图表之前、仅按字符串包含删除关联。

1B复用1A，不重新调查导入、解密或语音底层。背景模块与节点模块分别承担持久化和业务职责，不把它们继续堆入词频统计函数。

### 3.2 1B用户流程与交付范围

1. 主窗口点击“线下背景”，打开独立管理窗口，默认带入当前账号及会话／项目。
2. 新建背景：只要求标题或正文；时间、类型、关联范围按需填写，允许暂不绑定或日期未知。
3. 保存后可在背景窗口检索、编辑、删除；主窗口按需查看相关背景。
4. 从聊天证据点“标记关键节点”，或在背景窗口点“设为节点”，确认标题、类型和时间。
5. 分析页保留图表前置，增加“关键节点”紧凑时间线／列表；点击节点旁侧核对来源。
6. 点击“查找节点候选”显式运行规则，查看命中理由、原句和日期；确认、修改或忽略。
7. 返回时保留原会话、分析范围、筛选和阅读位置，背景窗口可继续独立使用。

首批不做任意附件导入、OCR、外部日历同步、全套项目管理、自动人物关系图或任务提醒。背景以本地文本和小规模结构化字段起步，节点先完成记录、候选和证据闭环。

### 3.3 规则候选的定位

规则是可检查的字面触发器，不是低成本的完整语义分类器。提供“项目进展”“交往事件”“通用事件”起始模板，用户选目标即可运行，详细触发表达可按账号编辑／停用。

规则输入为当前文字范围和显式所选背景；输出至少包括来源ID、命中区间、规则ID、理由、候选标题摘录及原始时间表达。输出默认为待确认，事件断言和进度未知，不因为命中“交付”就填“已完成”。

初始时间解析只覆盖明确日历日期及可无歧义确定参考日的相对日期，其余保留原句并请用户在确认时补充。阶段一不靠不断增加否定例外词表去模拟完整事件理解。

例如“下周可能交付”和“已经交付”都可以产生阅读候选，但规则候选不自动更新项目状态；“我们什么时候见面？”不能直接生成已经见面的事实节点。与节点有关的规则不影响现有词句筛选和普通搜索。

### 3.4 1B完成标准

背景窗口可独立打开、保存、关闭、再次打开；没有模型仍能完成完整流程。人工节点可混合引用聊天与背景，候选可确认／拒绝，时间未知有准确提示。背景数量和聊天统计分开；账号切换、并发编辑、关联来源删除及上下文返回均有明确结果。接口通过不能替代双窗口实际操作验收。

## 4. 线下背景管理窗口开发规格（规划）

### 4.1 窗口与主窗口协作

桌面采用**独立顶层pywebview窗口**，不是主页面右侧抽屉；复用同一FastAPI服务、Manager和数据根目录，不另起后端或加载另一份模型。建议前端入口为 `/?view=background&account_id=...`，从现有静态入口分流到独立组件，避免依赖尚不存在的SPA路径回退。

`NativeBridge.open_background(account_id, scope)` 负责创建／激活窗口；桌面实例同时仅保留一个背景窗口。浏览器诊断模式用独立标签承载同一视图。窗口入口不执行主App的阅读位置恢复／保存副作用。

行为契约：

- 窗口头部持续显示绑定账号与范围。账号切换后，旧窗口停止提交，提示重新绑定；未保存草稿留在内存，不写入新账号。
- 关闭背景窗口不停止服务；主窗口退出前检查子窗口未保存修改和正在提交的保存。取消退出则保留两个窗口。
- 保存成功才显示完成；保存失败保留表单与原因。长表单关闭时提供保存／放弃／继续编辑。
- 主、子窗口同条记录并发编辑使用记录修订号检查；冲突不以最后写入静默覆盖，返回最新版本供用户比较。
- “查看关联聊天”向主窗口传递稳定来源定位；主窗口保留返回状态，不把该次跨范围定位写进当前分析筛选。
- 成功编辑后通知另一窗口刷新相应记录；采用轻量修订轮询或桌面回调即可，不为此引入通用消息总线。

### 4.2 背景记录字段

| 字段 | 契约 |
|---|---|
| `id`、`revision` | 稳定ID、递增修订号；新增从1开始，编辑必须提供所见版本 |
| `title`、`body` | 保留用户原文；标题可由正文首行作默认值，非模型摘要 |
| `record_kind` | 经历／事实陈述、计划、个人判断、一般背景；由用户选择，可用默认一般背景 |
| `event_time` | 原始描述、起止、精度及可选参考日；允许未知 |
| `scopes` | 会话username／项目ID的绑定列表；允许空列表，不自动按名称推断绑定 |
| `people`、`tags` | 可选文本；联系人绑定须用户明确选择，不新增全局人物归并系统 |
| `created_at`、`updated_at` | 录入及编辑时间，与事件时间分开 |

“用户记录的事实陈述”表示记录类别，不表示程序已经核实客观真实性。个人判断作为原样资料存在；第三阶段不能把“我觉得他在回避”改写成已经确认的对方行为或动机。

### 4.3 存储与API

在现有账号 `archive.sqlite` 新增 `background_records` 和 `background_scopes`。正文和常用日期、修订字段置于记录表，范围绑定独立表；标签和可选人物字段可使用JSON。按实际查询增加范围、事件时间索引，不新增专门数据库或迁移框架。已有档案的表扩展不得破坏旧消息表及事务发布。

拟定接口（均未实现）：

| 接口 | 作用 |
|---|---|
| `GET /api/background?account_id&scope&from&to&q&offset&limit` | 账号内分页，返回总量和当前页；默认50条、上限100条 |
| `GET /api/background/{id}?account_id` | 正文和当前版本 |
| `POST /api/background` | 新建；显式account_id、字段及绑定 |
| `PUT /api/background/{id}` | 编辑；显式account_id及expected_revision；版本冲突返回409 |
| `DELETE /api/background/{id}?account_id&expected_revision` | 删除记录及绑定，同一事务处理证据依赖 |
| `GET /api/background/scopes?account_id&q&offset&limit` | 按需搜索可绑定范围，只返回名称与身份等必要字段 |
| `GET /api/background/export?account_id&...` | 显式导出所选背景为JSON，独立于聊天命中导出 |

静态路径 `/scopes`、`/export` 先于动态 `/{id}` 注册，避免路径被当成记录ID。数据API统一校验活动账号与请求账号，沿用当前账号切换错误语义；冲突处理只用于确有双窗口并发的记录编辑。

正文不放进 `/api/data-status`，不随状态轮询返回。范围选择器不能再次一次挂载全部联系人；保持服务端分页及按需搜索。导出复用现有原生保存流程，新增明确的背景导出模式，不改变原聊天TXT／JSON结构。

### 4.4 删除与保存语义

背景的记录及范围绑定一次提交，失败回滚。会话隐藏／清理不级联删除用户手工背景；绑定和节点引用保留可识别的来源状态，来源不可读时显示“来源已隐藏／已清理”。

删除背景前显示依赖节点数。删除时同时移除该背景的引用摘录，并使依赖它的机器候选及摘要失效；已确认节点保留用户编辑内容、标记证据缺失，允许用户继续修改或删除。后续索引删除对应条目。不要在用户删除后仍通过摘要或向量结果回显已删除背景正文。

本地用户资料和发布资源分离；升级保留背景，ZIP不包含任何账号背景。首批提供JSON导出作为人工备份，不扩展为跨账号自动同步。

## 5. 关键节点与事件模型（规划）

### 5.1 节点回答什么

节点是“值得保留并核对的一次事件或明确表述”，不等同于词频峰值、时间片段或语义簇。

| 任务 | 可记录的节点 | 不能从弱信号直接得出的结论 |
|---|---|---|
| 项目进度 | 需求确认、提出交付日期、报告阻塞、验收通过、延期或取消 | 只提到“完成”就认定项目已完成 |
| 交往情况 | 用户标记的重要见面／共同活动、明确的关系表述、联系安排及后续变更 | 从频率下降、迟回复或相似表达推断关系疏远／动机 |
| 通用事件 | 约定、发生的事项、后续变更及用户认为重要的记录 | 将设想、转述、提问直接当成已发生事实 |

“交往”不限于恋爱关系；默认采用可编辑的事件类型，不内置一条所有人都必须遵循的关系阶段链。若需要明确的关系阶段，先记录原文明确表述或用户人工设定，模型建议仍需确认。

重要性依据来自用户标记、选定任务中的里程碑类别、明确的状态／计划变化和可核对证据。统计突变至多是找线索的入口，不自动生成事实节点。

### 5.2 字段与生命周期

新增 `milestone_nodes`、`milestone_evidence`；第一阶段先存人工及规则结果，第二、三阶段只在现有对象上补充语义／模型来源。

| 字段 | 契约 |
|---|---|
| `id`、`revision`、`task_kind` | 节点身份、编辑版本、项目／交往／通用分析类型 |
| `title`、`description`、`node_type` | 可编辑陈述和事件类型；标题不替换引用原文 |
| `event_time`、`observed_at` | 事件时间及记录／消息中观察到该表述的时间 |
| `origin` | manual／rule／semantic／llm；人工确认后仍保留最初来源 |
| `review_state` | candidate／confirmed／rejected，与事件进度分开 |
| `assertion_kind` | 已发生陈述、提议、承诺、假设、个人解释或未知；阶段一规则默认未知 |
| `progress_state` | 可选的计划中／进行中／受阻／完成／取消／未知，属于事项而非审核状态 |
| `scope_snapshot` | 账号内实际会话集合、可选项目ID和识别日期／条件 |
| `evidence` | 聊天或背景引用、修订／跨度、必要摘录及支持／修订／反对角色；来源状态为current／stale／missing，与审核状态分开 |
| `supersedes_id` | 可选：明确修改了哪个旧节点；不得仅因时间较晚而自动填入 |
| `run_id`、`method_version` | 机器候选对应的任务、规则／模型与配置版本，供解释和重跑 |

状态迁移：人工新建可直接确认；规则／语义／模型输出先进入candidate；用户可编辑后确认或拒绝。重跑不覆盖confirmed节点，也不自动恢复用户已拒绝的同来源同类候选。以来源ID、跨度及类别进行重复检查，不按标题字符串或向量相似度静默合并事件。

不展示未经校准的“事实置信度百分比”。展示原始证据、命中／抽取理由及待确认状态。程序能校验来源ID和摘录位置合法性，不能靠引用存在就证明陈述成立。

### 5.3 项目状态变化示例

以下均为规格用合成情景：

| 原始资料 | 第一阶段 | 第三阶段可提出的候选 |
|---|---|---|
| “下周可能交付” | 规则命中位置，用户定含义 | 交付设想；日期不确定；不能标完成 |
| “确认周五交付” | 原文标记／规则候选 | 交付承诺；周五按消息参考日解释 |
| “已经交付，等验收” | 原文标记／规则候选 | 报告已交付，仍待验收；不能等同验收完成 |
| “刚才版本有问题，撤回重发” | 保留后续原文 | 对相关交付节点提出修订；不删除旧事件 |
| 线下背景：“周六现场验收通过” | 用户背景／人工节点 | 采用所选用户记录并明确其来源，不能伪造聊天出处 |

节点时间线同时展示原节点与明确修订。一个人报告完成与群体一致确认是不同证据；“后来没有人再说”不补成共识。交往分析同样区分明确事件、个人感受与对方表述。

### 5.4 节点查询与原文入口

拟新增 `GET/POST /api/milestones`、`GET/PUT/DELETE /api/milestones/{id}`，以及 `POST /api/milestones/{id}/review`。列表默认分页50条，支持范围、事件时间、审核状态、任务类型和来源筛选；修改及审核都携带account_id和expected_revision。

主分析页节点图／列表仍位于基础统计图之后；背景独立窗口也可进入相关节点。时间轴区分计划和已发生，未知日期单列、区间按区间呈现。点击后在现有旁侧证据区分组显示聊天和背景，各自进入原文／背景详情，保留返回状态。拒绝候选从默认列表移出，可按审核状态找回。

候选扫描必须由用户触发；大范围用任务接口分页／批处理，返回任务ID，不在现有 `POST /api/analysis` 请求里自动扫描全库。任务对象固定账号、范围、方法版本，状态含排队／运行／完成／失败／取消及阶段内done/total。任务生命周期规范见第8节。

## 6. 第二阶段：本地语义检索与节点证据召回（规划）

### 6.1 交付目标和先后顺序

先完成“找相似讨论”，再将其用于节点证据补全。不把聚类或自动语义归并作为本阶段前置条件。

1. 建立“字面不同而应相关”的任务集及明显不相关反例。
2. 在相同语料、范围上比较字面检索与候选本地嵌入；选模型、切分和排序方案。
3. 用户选择范围后准备索引，展示可用与尚未索引数量。
4. 新增独立的语义查询输入；结果包含相似分数、来源、实际区间和阅读入口。
5. 用户选人工／已确认节点的描述或证据，点“查找相关记录”，召回其他说法的候选证据，人工加入或排除。
6. 用户显式选择的背景可以独立召回；聊天与背景分组，禁止混入消息计数。

例如“已经把包发过去了”可能补足“交付”的相关证据，但相似度本身不能判断交付对象、成功状态或是否被撤回，仍需原文核对。用户别名继续是明确配置，不由向量结果改写。

### 6.2 索引单元与匹配范围

使用保留会话、发言者和顺序的片段／子段。长片段按模型输入限制分割，保留消息ID映射；不以展示页或当前50条分页作为索引边界。每个分块必须能回到真实消息集合，重叠子段的检索展示不能重复计作不同消息。自然时间片段可作初始切分边界，但不称为确定主题。

首版采用明确的筛选后评分契约：

1. 先以账号、会话、日期、发送者、类型、成功转写条件及现有字面 `q` 形成合格消息集合E。新增 `semantic_query` 是语义问题；保留 `q` 就是两者取交集，界面允许显式清除字面条件，不能自动忽略。
2. 在完整时间顺序中形成E内的连续子段；被排除消息保留为边界，不能删掉后将两侧拼成一段。检索向量和最终相似分数只由这些合格文字构成，范围外消息不能贡献排名。
3. 已有向量只有在对应文字和消息集合均未改变时才能复用。一个原分块同时含合格与不合格消息时，必须为合格连续子段重新准备向量；不能继续用原混合块分数，仅在显示时隐藏不合格文字。
4. 范围变化需要重新准备的部分通过内容任务显示进度。尚未覆盖全部E时，明确展示已索引／未索引数量，不以现有top-k假装覆盖完整新范围。首版只准备用户当前选择的范围和实际可复用条目，不预计算全部筛选组合。
5. 返回命中证据集合R须属于E；按需阅读的上下文集合C可以超出E，但单列为上下文，不参与该次向量评分和命中数量。背景遵守同样的范围／版本约束并单独返回。

这个方案可能增加频繁改变筛选时的准备成本，必须纳入第6.4节延迟和复用测量；不能用范围外信息参与排名来掩盖成本。

不同来源分别索引，背景携带record_id和revision。表面相似的两人同名、计划与完成、否定与肯定都需要反例评测；自动将它们合并成同一事件不在本阶段交付内。

### 6.3 计算、依赖与失效

本地模型由用户事先准备，首次点击不隐式下载。后台worker按需加载，模型推理不放进FastAPI事件循环或桌面宿主；基础包没有模型时保留第一阶段全部能力并说明准备入口。内容运行时与语音依赖分别声明，不能默认借用开发机Conda或强制安装完整语音包，不以GPU为必要条件。

首版采用可测的分批向量计算及账号内持久派生文件；中小范围先精确余弦检索，搜索成本 O(Md)，M为合格分块数、d为向量维度。比如20,000×768的float32向量仅矩阵约58.6MiB，模型及文本元数据另计，这只是容量计算，不是本项目实测。只有精确扫描在目标范围下成为瓶颈，才评估ANN索引，不先引入向量数据库或后台服务。

模型／切分配置变化重建相应索引；导入正文变化、成功转写更新、消息清理及背景编辑／删除使对应派生条目失效。持久缓存出现时再增加必要的数据修订号或提交后失效钩子，覆盖上述实际写入入口，不用逐请求全库哈希代替失效设计。只在事务成功提交后发布可查询版本；取消或失败不发布半成品。

拟新增 `POST /api/semantic/index`、`POST /api/semantic/search` 和节点相关证据查询入口，复用第8节任务状态。索引覆盖数、查询合格范围、top-k返回数分开；top-k不是全量提及消息数，相似度不是概率。

### 6.4 完成条件

语义检索在预先固定的跨说法任务集上比字面基线补足相关证据，并报告Recall@k、Precision@k、否定／同名／时序错误及人工相关性判断。选型前固定k和可接受误报预算，开发样例与验收样例分开，不能以负例明显退化换取表面召回增益。不能只展示成功例子或只评词面更相近的查询。

固定范围的模型、索引规模、首次／再次准备时间、查询延迟、峰值和常驻内存必须记录。具体模型及资源预算在比较后确定；未做选型前不承诺秒级索引或固定包体。关闭模型、缺模型、索引不完整、更新失效均有可恢复界面。语义分组／聚类保留为后续可选项，不阻塞本阶段验收。

## 7. 第三阶段：节点识别、进展整理与摘要问答（规划）

### 7.1 交付顺序

先做**选定片段结构化事件抽取**，再扩展同一事项的跨片段节点时间线，最后做带引用摘要与问答。阶段三可以先接字面检索和人工背景，不要求阶段二所有可选能力完成；若要覆盖不同说法，验收必须同时报告有无语义召回的差别。

项目进度与交往事件共用节点和证据契约，但分别使用任务字段和样例。项目可整理承诺、交付、阻塞、验收、延期；交往可整理重要活动、安排及明确表述，不从统计变化自动判定情感或关系状态。

### 7.2 抽取管线

1. 固定识别范围、任务类型、用户背景集合及版本。
2. 用字面／语义检索取得候选片段，并按同一会话及时间组织有限上下文，保留发言归属。
3. 在规定输入预算内分批抽取结构化事件：主体、行为／表述、对象、事件时间、断言类型、进度状态和证据引用。
4. 程序验证字段、来源ID、摘录跨度和版本。非法引用的陈述不发布为有效候选；解析失败可重试，失败原因可见。
5. 对候选事项补查同范围内后续修订、否定、不同主体和背景冲突；超出范围的后续资料只提示用户扩大范围。
6. 形成待确认节点，按证据关联组织重复候选，提供逐项编辑、确认、拒绝和查看来源。
7. 对已核对的节点／证据生成进展整理、摘要和回答，逐项引用来源。

分批处理不能丢弃批次间的事件延续和修订：用结构化候选及来源映射作为跨批汇总输入，再回到原文核对，不能只递归摘要并丢失证据。不得先让模型生成完整故事再补引用。

### 7.3 背景资料如何参与推理

用户先选择是否纳入背景及具体记录。输入中对聊天与背景分别标注来源、记录类型、事件时间、录入时间和版本；个人判断、计划与已发生陈述分别编码。每个结论引用实际来源，不把用户回忆写成聊天发言。

当聊天说“尚未验收”、背景写“已现场验收”，先检查事件时间和对象；仍不能消解则并列显示差异及依据，不设置“背景永远优先”或“最后一条永远正确”的规则。没有聊天支撑的用户记录可以单独构成用户确认节点，来源必须清楚。

每项输出声明本次已检查范围和未覆盖部分。“当前找到的最后一次明确表述”与“最终真实状态”分别措辞；截断日期、资料不全或未转写语音可能使后续变化不可见。

### 7.4 模型和结果管理

生成式模型按需本地调用，模型及运行依赖提前准备；未安装时不影响背景CRUD和人工节点。模型设置和运行入口与语音API分离。本轮不默认上传聊天或背景，在线文字模型若另行纳入需求，必须单独定义用户选择、实际发送来源及范围。

保存模型／方法版本、运行范围、引用版本、运行时间和用户审核结果。后台重跑只更新机器候选，不覆盖人工修改和confirmed内容。来源发生改变时标记相关输出待复核；用户删除背景后移除派生回显，不继续展示旧缓存正文。

不让生成模型计算全库词频、消息分母或“完整命中数”。如回答包含统计，调用第一阶段确定性查询，并独立说明模型阅读选段与统计全集。

### 7.5 完成条件

至少覆盖：主体归属、否定、提问、设想、承诺、报告完成、后续撤回、同名不同对象、跨批次修订、时间不确定及背景冲突。逐字段检查事件时间、断言类型和状态，逐陈述检查引用支持与后续遗漏，报告误报／漏检。

引用ID有效率须100%；这只证明引用合法，不能替代事实支持审查。带引用但推理错误仍判失败。核心验收样例中不得把设想／提问判成完成、把个人感受归到对方立场或覆盖用户已确认节点。开放语料报告实际质量与未解决错误，不以语言流畅度代替验收。

### 8.1 职责与拟改动位置

### 8.2 任务生命周期

目前Manager只有一个维护executor及维护任务记录，不能把候选扫描或模型任务冒充“档案更新”，也不能覆盖维护进度。

1B首次实现耗时候选扫描时，增加最小的账号内内容任务对象和单并发执行入口，API建议为 `POST /api/milestone-runs`、`GET /api/content-jobs/{id}`、`POST /api/content-jobs/{id}/cancel`；第二、三阶段复用任务状态约定，不预建多引擎调度平台。

任务固定账号、输入范围及版本，返回阶段名和done/total；取消在批次边界生效。阶段输出只有在完整提交后可见，失败保留已发布结果。维护提交后使受影响内容任务结果失效；运行期间的版本变化在发布前检查，不能把旧输入结果标成最新。

维护任务的取消及退出改进另见[易用性方案U3](usability-improvement-plan.md#5-u3长任务取消进度和退出)。U3验收前保持下述维护等待规则；验收后维护也支持“停止任务后退出”，须按其快照、导入事务和逐条转写的发布边界停止。内容任务仍保留独立状态；退出时若两类任务同时存在，须分别安全停止，并先处理背景窗口草稿／保存，不能因其中一类停止就关闭服务。

内容任务单并发，模型按需在worker中运行；长任务可取消，不能阻塞普通阅读。主窗口关闭先处理未保存修改和保存提交；有内容任务时提供继续使用或取消内容任务后退出。选择后者先请求取消，待当前批次停止、worker及其子进程清理完毕，再关闭子窗口和服务；等待期间显示正在停止，尚未停止不能提示退出完成。首版不支持关窗后脱离宿主继续运行内容任务。归档维护任务沿用当前等待完成、阻止退出的规则，不因取消内容任务而终止维护。账号切换不将旧任务状态或输出归入新账号，旧账号任务仍按其固定身份处理。

## 9. 验收数据与检查矩阵

### 9.1 数据与效果

合成数据用于可重复的正反对照和写入操作；真实样本仅在明确授权范围内只读使用，不复制正文进日志／截图或发布包。除规则简单样例外，必须包含多样、低重复且候选量接近目标范围的数据，避免再次用重复样例掩盖规模问题。

| 场景 | 应验收结果 | 阶段 |
|---|---|---|
| 背景晚录入、事件发生较早／日期未知 | 按事件时间排序，未知单列；不按录入日期伪造事件顺序 | 1B |
| 两窗口同版本编辑、切账号后保存 | 冲突可恢复；拒绝跨账号保存；草稿不丢到另一账号 | 1B |
| 绑定项目成员变化、会话隐藏或清理 | 当前范围明确；人工背景保留，失效来源有提示 | 1B |
| “可能交付／确认交付／已交付待验收／撤回” | 规则不擅自确认；第三阶段区分断言和状态并保留修订 | 1B、3 |
| “什么时候见面”与线下见面回忆 | 提问不变已发生；背景与聊天出处分开 | 1B、3 |
| 一节点引用多消息及多背景 | 引用去重；节点数、来源数、聊天提及数各自正确 | 全阶段 |
| 删除背景 | 聊天统计值不变；相关派生内容失效，不回显已删背景 | 全阶段 |
| 修改成功转写 | 按原有口径重新计算词频／命中等结果，受影响的引用和派生内容失效；不能要求统计值保持不变 | 全阶段 |
| 同事项换说法、相似词不同事项 | 语义召回相对字面基线的收益和误报可量化 | 2 |
| 分块重叠、筛选边界、未索引部分 | 结果不重复计数；不把top-k当完整命中；覆盖清楚 | 2 |
| 背景判断与对方表述冲突、后来推翻 | 来源及时间并列；不强行合成单一事实或最终共识 | 3 |
| 假引用、漏掉后续、跨批次事件 | 引用验证能拒绝；质量审查能检出语义错误及遗漏 | 3 |
| 长列表、首用、关闭模型、取消重跑 | 分页／虚拟化、恢复路径和第一阶段功能均正确 | 全阶段 |

保留现有词句、别名、关联、两期分母、普通搜索、账号隔离、成功转写和上下文边界回归。背景增删不改变任何既有聊天统计；语义结果和模型阅读范围有独立标签。

### 9.2 性能和界面验收

每次新增计算先测当前提交基线，再测相同数据、范围与机器。记录总字符数、候选量／分块数／背景量、首次与重复运行、阶段时间及各进程峰值和常驻内存，不将不同进程数值直接相减。

第一阶段1B的初始验收目标（目标，不是已测成绩）：10,000条合成背景下默认50条列表首屏1秒内可操作；任务触发后1秒内显示已接受／排队／阶段反馈。原11,352条只读分析范围作为可获得授权时的回归样本；同机稳定预热重复测量的完整分析中位数不应比开发基线回退超过20%，超出须定位并解决，不能通过缩范围达标。

第二、三阶段在选型时冻结模型、CPU／GPU条件、数据规模、质量指标及可接受耗时／内存预算，再进入集成。首屏不等待全库建索引；进度真实按阶段显示，不能用虚假百分比掩盖不可测时间。

必须实际走通：主窗→背景独立窗口→保存→标记节点→分析时间线→聊天／背景证据→上下文→返回；双窗口并发编辑与退出；模型阶段另加索引失效、任务取消、缺模型、重跑和用户审核保留。统计对账与API成功不能替代内容可读性和窗口操作验收。

## 10. 交付、决策与剩余边界

每次功能实施更新README当前行为及验收记录；改前端先构建，再按README同步已有基础版和完整语音版两个目录。新增Python模块加入 `scripts/build_portable.py` 明确资源清单；依赖变化同步对应锁定文件和完整构建。实际根目录cmd入口和随包运行时使用隔离档案检查，发行ZIP是否重打按该次需求决定。

本次文档采用的设计决定：独立原生背景窗口；本地账号SQLite保存背景；先交付无模型手工和规则闭环；嵌入只补召回；生成式模型负责完整语义事件抽取但不代替用户审核。它们是后续实施基准，尚未编码或验收。

实施前仍需通过样例解决的技术选择：具体嵌入／生成模型、分块尺寸、模型包体和资源预算、语义融合排序参数。采用评测决定，不在开发文档里虚构选型结论。任意附件导入、跨账号人物归并、在线文字模型及自动关系阶段评分不属于上述承诺范围。
