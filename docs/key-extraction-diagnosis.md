# 跨电脑密钥提取失败：代码侧诊断

2026-10-18。故障机器最初运行微信 4.1.13.65，本机微信 4.1.15.55；用户反馈更新和管理员运行后仍然失败。本次没有读取真实微信进程、聊天数据库或密钥，也没有修改应用程序与发行包。以下将代码中能够复现的问题与故障机器尚待确认的触发条件分开记录。

## 故障机器的目录截图提供的证据

微信设置显示存储根目录为 `C:\Users\chard\xwechat_files`，应用显示该目录下某个 `wxid_…` 账号的 `db_storage`。两条路径的父子关系符合当前检测逻辑，所示数据库路径全部由 ASCII 字符组成。因此，“中文源数据库路径”不适合作为本次故障的主要解释，选错到总目录或重复拼接 `xwechat_files` 的解释也缺乏支持。截图没有显示应用安装目录与结果输出目录，不能据此确认所有运行路径均为 ASCII。

`auto_detect_db_dir()` 读取配置后枚举账号目录，直接返回第一个候选；它不核对当前登录进程对应哪个账号。截图支持存储根目录一致，不能证明该 `wxid_…` 目录属于当前登录账号。若存在历史账号或多个账号，目录检查仍可能通过，进程中读到的候选密钥却无法通过所选数据库的 HMAC 校验。

此前错误窗口已经显示目录与账号已确认。若对应同一次失败，按代码至少已找到 contact/contact.db、消息分片，并成功读取过通讯录文件头。因此，把问题简单归因于源目录不存在或整个目录无法读取也不合理；进程内存权限、其他数据库的读取权限仍是独立问题。

截图不包含内存区域大小、候选密钥统计或子进程异常，对“大区域漏扫”与真实微信布局变化均没有新增支持。源路径是 ASCII 也不能排除输出编码异常，因为首条提示语本身含中文；微信界面显示中文不足以确定 Windows 管道输出编码。

## 新截图：优先核对实际保存的源目录

用户后续截图显示微信设置的存储根目录为 `C:\Users\chard\xwechat_files`，另一张目录选择界面停在“文档 > WeChat Files”，其中列出两个 wxid 目录。两张图展示的是不同位置；第一张路径本身没有中文字符。第二张只能证明选择界面正在浏览该位置，不能证明应用已经检测、确认或保存了其中某个目录，也不能确认哪个账号正在登录。文件夹修改日期不足以判断内部聊天数据是否仍更新。

`desktop.py` 的 `choose_directory()` 调用系统文件夹选择器时没有传入起始目录。`frontend/src/main.tsx` 中“选择目录”与“查找本机目录”是两个不同入口：前者打开选择器；后者调用 `auto_detect_db_dir()`，结果按代码必须以 `xwechat_files/<账号>/db_storage` 形式匹配。因而截图中的 `WeChat Files` 浏览位置不能直接当作自动检测结果；若界面确实将其显示为检测结果，还需确认远端运行包的实际代码。

`maintenance.inspect_directory()` 要求所选根目录直接含有 `contact/contact.db` 与 `message/message_*.db`，才可确认账号。因此“文档/WeChat Files”父目录本身通常不能通过准备阶段。若用户此前已进入提取阶段，实际保存的 directory 应为另一个更深层目录，或运行包与本机源码存在差异。

诊断优先级据此调整：先核对应用实际保存的完整 directory 是否位于微信设置的存储根目录内，且账号与当前登录者对应。源目录不对应当前进程时，即使提取到合法候选密钥，也可能全部 HMAC 校验失败；这能解释升级、管理员运行均无效。先前复现的漏扫与编码缺陷仍成立，但截图没有证明它们在故障机器触发。最小新增证据是应用数据设置或当前账号记录中的已保存完整源目录。

## 已复现：扫描主动跳过大块可读内存

`wcdb_key_tool_windows.py` 的 `enum_regions()` 仅接纳 `0 < mbi.RegionSize < 500 * 1024 * 1024` 的区域。达到 500 MiB 的整个区域被排除。新版 Config.Cipher 路线和旧版 raw key 回退都使用这个枚举器，因此回退不能补救。

Config.Cipher 定位需要先扫描名字字符串，再扫描引用该字符串的指针与长度组合。如果其中任何一项只存在于被排除区域中，就无法继续定位配置对象，即使操作系统允许读取。此处的 RegionSize 是连续虚拟内存区域大小，并非任务管理器显示的整个进程内存用量。

验证包括两层：

- 合成 WinAPI 夹具提供相同配置对象、密钥与 HMAC 页面，只改变区域大小：4 KiB、499 MiB 均验证 1 个 salt；500 MiB、512 MiB 均提取失败。
- 在本次探测进程中实际 VirtualAlloc 分配 4 KiB 与 500 MiB 可读区域，使用生产代码原样抽取的枚举器检查。ReadProcessMemory 对两者都成功，但生产枚举器仅收录前者。内存随检查释放。

这是确定存在的漏扫缺陷。是否为另一台电脑的根因，取决于该机相关字符串或引用是否落在这样的区域；目前没有该机内存区域证据。

## 已复现：后台输出编码可在扫描前使程序退出

维护进程使用 `capture_output=True` 启动工具，工具未固定 stdout 编码。`cmd_extract()` 一开始就打印中文“数据库目录”。若目标 Windows 的管道输出编码为 cp1252，这一步直接抛出 UnicodeEncodeError，尚未进入数据库收集与进程扫描。即使路径本身全为 ASCII，也会失败。

对空的合成目录分别设置 stdout 为 cp1252、GBK 和 UTF-8：cp1252 在首条输出处抛 UnicodeEncodeError；其余两者正常走到“没有数据库”的预期 SystemExit。随包 Python 3.11.9 本机实际 stdout 编码为 GBK、UTF-8 mode 为 0，因此本机能打印中文不能证明另一台机器能。

这是确定存在的环境依赖。是否解释目标机器故障，取决于该机实际输出编码；管理员权限和微信版本均不能修复这类异常。

## 已复现：tasklist 数字解析依赖区域格式

`_get_pids_windows()` 通过 tasklist CSV 解析 PID 与内存用量，内存字段只移除逗号与 ` K` 后调用 int。合成 CSV 中 `1,000 K` 能解析，`1.000 K` 和包含不换行空格的分组数字均抛 ValueError，导致整个提取退出。

这里的内存值只用于排序，却成为扫描前的失败点。此测试证明解析器的限制，不证明故障机器实际返回这些格式。若两台电脑使用相同区域格式，该项解释力较弱。

## 有版本敏感性，但未证实两个版本存在布局差异

扫描器固定使用节点偏移 `+0x28`、配置对象偏移 `+0x88`，以及固定的 32 字节 XOR 掩码。找到名字字符串并不意味着后续布局与掩码匹配。合成夹具将配置偏移从 0x88 改为 0x90，或改变掩码一个字节，均从成功变为提取失败。这个对照仅证明算法依赖这些条件，不能证明真实版本已经改变它们。

上游当前源码与另一份公开 Windows 实现也使用相同掩码和偏移。后者报告曾在 4.1.13.12 使用 Config.Cipher 路线，故不能把整个 4.1.13 系列简单判定为不支持，也不能据此保证 4.1.13.65 或 4.1.15.55 一定兼容。

## 错误窗口没有呈现底层失败原因

`maintenance.py` 在子进程退出码非零或没有输出密钥文件时，统一抛“确认微信登录、检查读取权限”的 RuntimeError。上述编码异常、数字解析异常、扫描零命中、数据库文件读取异常都会显示同一提示。窗口中的 `maintenance.py:211` 是重新抛错位置，不能作为原始故障位置。

若扫描已找到部分有效密钥，当前工具会保存部分结果并成功退出。因此本截图更符合扫描前异常、一个有效密钥也没有找到，或输出文件写入失败；单纯缺少少数未打开数据库的密钥通常不会在此处产生截图中的失败。

本机基础版、完整语音版应用目录及两个发行 ZIP 内的 `maintenance.py`、`wcdb_key_tool_windows.py` 与当前源码逐字节相同。排除了本机这些产物中两份相关代码不同步；不能替代检查远端实际使用的包。

## 下一步应做的代码修改

移除整区 500 MiB 排除，让已有的分块扫描处理大区域；旧版回退也使用分块读取。固定工具输出编码，避免中文打印中断提取。进程枚举不应因排序用的内存字符串解析失败而终止。增加不含密钥、salt、账号路径和内存原文的阶段诊断：进程打开结果、可读/跳过区域数与字节数、名字命中、引用命中、blob/候选/校验数量、失败阶段及异常类型。由维护层展示这些结构化诊断，不直接公开原始 stdout/stderr。

这些修改分别修复确定缺陷与恢复定位能力。另一台机器更新微信、提高权限后仍失败，并不足以在漏扫、编码和布局不匹配之间作唯一选择。
