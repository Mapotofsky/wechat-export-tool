# 分析等待与内存占用：问题、实现与验证报告

日期：2026-10-25。本文记录本次已完成的性能修复，解释执行复杂度、数据结构、测量条件和验证边界。完整功能验收见[分析改进验收记录](analysis-improvement-acceptance.md)，产品行为见[README](../README.md)。

## 1. 问题与结论

用户进入分析页后，界面长时间停留在“正在统计完整查询范围”，同时观察到较高内存占用。核对实际入口后，确认运行的是完整语音便携版程序副本。

本次定位到三个具体开销来源：

1. **分析匹配按“候选 × 全语料”执行。** 真实语料候选约11万项，逐候选重扫全文导致计算量失控。
2. **前端一次挂载全部17,860个会话。** 滚动容器没有减少DOM、React及布局对象数量。
3. **状态轮询重复发送整份通讯录。** 会话接口已提供目录，状态展示却每1.5秒再次接收这份未使用的数据。

已改为请求内多模式字面匹配、减少临时及展示元数据、会话列表虚拟化和精简轮询响应。真实单会话完整分析约7–9秒返回，统计范围和候选规模保留。独立分析进程仍需数百MiB，不能将本次修复描述为已经消除所有内存成本。

## 2. 后端计算为何失控

设消息数为 N，候选数为 V，可分析文本总字符数为 L，全部实际匹配位置数为 Z。

旧版 `content_index()` 的核心执行结构是：

```python
for term in vocabulary:
    for message in messages:
        spans = literal_spans(message.text, term, ignore_structured)
        # 累计提及消息、出现次数、日期、位置和原文形式
```

`literal_spans()` 在每次调用中重新识别消息的URL／wxid忽略跨度、执行小写转换，再做子串查找及边界判断。因此不只是 O(VN) 次调用，主要文本处理量接近 **O(VL)**，还伴随重复正则扫描和字符串分配。

经授权只读测量的真实范围：

| 指标 | 数量 |
|---|---:|
| 全部消息 | 11,352 |
| 可分析文字消息 | 9,284 |
| 候选表达 | 110,142 |
| 候选—消息检查量 | 约12.5亿次 |

读取档案约0.12–0.19秒，旧版新词发现约0.94秒；主要等待发生在后续候选索引。旧版诊断进程在该阶段长时间未返回，累计约50分钟CPU时间后终止，未取得完整分析耗时。这个下界不能作为一次完成的基准，也不能用于计算精确加速倍数。

### 2.1 候选规模的来源

普通短语枚举连续2–6个token窗口。对长度为 k 的token块，窗口枚举量是 O(5k)，并非指数增长。真实消息中的措辞、数字、编号和组合不同，导致去重后的全局词表仍可达到11万项。

根本问题是把较大的候选词表逐项拿去重扫全集，而不是短语窗口本身具有指数复杂度。

此前600条重复度较高的合成消息仅生成145项候选。它验证了部分统计行为，却没有覆盖真实语料中 V 的变化；此前性能验收对此覆盖不足，不能用消息条数的线性倍数推算真实耗时。

## 3. 多模式匹配如何替代逐候选扫描

`analysis_lexicon.LiteralMatcher` 实现请求内的Aho–Corasick式匹配：

1. 对候选词表建立trie。
2. 广度优先构建failure links，并继承终止输出。
3. 每条消息只执行一次小写文本扫描，同时产生多个候选匹配。
4. 对输出执行原有边界及结构化忽略跨度检查。
5. 将合法匹配保留为原文字符区间，用于统计和后续位置判断。

文本扫描部分从 O(VL) 改为接近 **O(L + Z)**。完整分析接口不能直接标成这个复杂度：还包含trie及failure/output构建、输出区间检查、与忽略区间的重叠判断、分词、候选生成、统计及Python对象分配。

匹配器在请求内构建、使用并释放，没有新增持久索引。两期分析分别处理各自语料，缺少候选的另一侧计数也采用批量匹配补齐；空时期不构建无用匹配器。

### 3.1 保持的业务口径

- 中文仍按字面子串匹配，英文仍忽略大小写。
- 英文、数字及 `C++`、`GPT-4`、`v1.2` 等保留相同匹配边界。
- 开启结构化忽略时，仍排除与URL／wxid跨度重叠的匹配。
- 返回全部合法重叠位置，不改为只取最长匹配。
- 保留原始字符位置，不把别名组名替换进原文。
- 没有缩小日期、截断消息或减少候选词表来换取速度。

新增回归测试将批量匹配与单表达 `literal_spans()` 对照，覆盖大量重叠子串、符号专名、数字、URL和混合文本，逐项比较匹配区间。

真实数据中，优化后的 `content_index()` 约2.4–2.7秒，完整分析约7–9秒。二者不是同一计时范围：其余时间还包括分词、片段处理、统计及结果组织。本次没有对余下每个环节完成精确归因。

## 4. 后端内存调整

旧实现同时持有消息字典、token及词性位置、候选集合、命中位置、日期集合、原文形式、示例摘录，以及新词ngram与上下文统计。峰值来自多个表示同时存活，不能简单归因于“读取了全部消息”。

其中还有一段未被调用方使用的结构：

```python
sets = [
    {term for term in active if i in positions[term]}
    for i in range(len(rows))
]
```

它额外执行 O(NV) 次成员检查并保存冗余命中表示。它不是实际分配 N×V 单元的稠密矩阵；本次删除的是无用遍历和冗余集合。

其余调整按后续用途控制数据保留：

| 数据 | 当前处理 |
|---|---|
| 全部原始候选计数 | 保留，不因未展示而删除 |
| 关联所需位置 | 共同提及至少2条，单次提及候选无需为关联保留完整位置结构 |
| 展示词、有效短语、新词、别名成员 | 保留所需位置与明细 |
| 短语支持门槛为1 | 仍保留相应候选明细，不以优化覆盖用户配置 |
| 低支持、未展示候选的摘录与形式 | 不再全部提前构造，原文仍可重新回查 |
| 请求内token缓存 | 完成候选生成后释放不再需要的引用 |
| 日期分布 | 按命中累计，避免逐日期重扫命中集合 |
| 代表摘录 | 先去重复文本，减少相同回复反复参与选择 |
| 分析设置和会话元数据 | 只读取必要分析设置及所选会话元数据 |

新词发现原先为候选保存支持消息ID集合，现在在每个去重文本内先做局部候选去重，再累计支持数；左右边界上下文仅对达到支持条件的候选进一步统计。支持量、PMI及边界熵门槛不变，不修改全局词典。

本次证据支持“存在较多冗余分配”，**没有证明存在持续增长且不可回收的内存泄漏**。Python分配器可能保留内存页，请求结束后的工作集不立即回落不能单独证明泄漏。

## 5. 前端会话列表与轮询

### 5.1 列表虚拟化

旧版直接对全部 `chats` 执行 `map()`。滚动容器仅限制可见区域，不限制React元素、DOM节点、布局对象和可访问性树规模。真实列表下，Chrome页面渲染进程工作集曾约900MiB，自动化读取页面结构也超时。

新增 `frontend/src/SessionList.tsx`：

- 根据行高建立前缀偏移，以二分查找定位滚动位置对应的行。
- 仅渲染可见行及前后约6行，使用上下占位高度保留完整滚动范围。
- 键盘按全局行号定位，必要时先滚动、挂载，再恢复焦点。
- 完整 `chats` 数组继续参与筛选和批量操作，显示行数不限制选择或分析范围。
- 搜索原因在列表内保持紧凑，完整内容保留为悬停提示。

部分“已选项是否仍在当前列表”的反复线性查找也改为Set查询，避免完整全选时再触发明显二次复杂度。

实际验证能滚至第17,860行、方向键移至第17,859行、完整全选17,860项；筛选、Shift+F10菜单及Escape焦点返回正常。

### 5.2 状态轮询精简

前端每1.5秒轮询状态，旧响应的 `config` 包含约1.8万项 `contact_directory`。前端状态展示不使用它，会话接口已单独提供目录。

当前从状态返回对象中移除该字段，存储中的通讯录保留。同一只读验收配置中，响应由2,479,090字节降为3,040字节。

这里没有消除全部后端读取成本：`Manager.status()` 仍先通过 `archive.config()` 读取配置，再移除该字段。此次消除的是重复序列化、传输、前端解析和持有开销，不能宣称后端完全不再解析这份配置。

## 6. 实测结果与验证边界

真实聊天经用户明确授权，只通过SQLite `mode=ro` 与 `PRAGMA query_only=ON` 访问；不执行真实档案或账号设置写入。只读界面中的阅读位置保存在内存，禁止维护和配置写入。保留匿名规模、耗时及差异指标，不保存真实聊天正文或截图。

### 6.1 时间与内存

| 测量 | 结果 | 条件 |
|---|---|---|
| 真实单会话完整分析 | 8.5272／7.4334秒 | Windows 10.0.26300、Conda Python3.10.12，连续完整重算 |
| 同次进程峰值工作集 | 379.95MiB | 独立分析进程，不含浏览器及桌面宿主 |
| 基础便携版实际分析副本 | 8.0159秒、峰值352.90MiB | 随包Python3.11 |
| 完整语音版只读页面点击分析 | 7.772秒 | 实际app中的API、分析模块及构建静态资源 |
| 多样化合成范围 | 17.0227秒→2.5762秒 | 相同1,200条消息及范围，候选均3,155项 |
| Chrome页面渲染进程 | 旧约900MiB，最终流程后约172MiB | 同机只读验收观测；不是桌面总内存 |

真实分析仍覆盖11,352条消息、9,284条文字，候选仍为110,142项。分析进程峰值与浏览器工作集属于不同进程、不同测量条件，不能直接相减计算总体节省，也不能把任何一项当成应用总内存。

### 6.2 正确性和交互

- 真实数据160个展示表达及嵌套原项，逐项用单表达字面回查核对：提及消息数和出现次数差异0，总量等于实际读取消息数。
- 一个界面表达显示2,856条提及，旁侧回查也是2,856条；原文高亮、上下文及返回可用，完整范围保持11,352条。
- 图表仍在前，原文按需阅读。列表常见窗口挂载约11–18行，完整选择范围不变。
- 相关45项自动化检查通过：匹配／只读／轮询5项、词句扩展9项、分析12项、搜索7项、HTTP1项、可用性3项、语音相关8项。未调用真实语音识别或外部转写服务。
- TypeScript/Vite构建通过；基础版桌面与根目录cmd入口使用隔离合成档案完成启动，随包子进程退出码0。

这不是对全部11万候选的逐项人工验收，也不是对真实全库性能的证明。不能由本次单会话测量推断所有分析范围都能在9秒内完成。

## 8. 限制

词典、解析消息、token、trie及匹配位置仍需要内存，更长正文、更多候选或更多实际匹配位置仍会增加成本。当前只证明已复现瓶颈得到修复，没有完整内存泄漏审计、真实全库压力测试或干净Windows安装验收。

此次不包含嵌入、自动语义归并、聚类、摘要或问答；匹配提速没有改变字面证据的含义。
