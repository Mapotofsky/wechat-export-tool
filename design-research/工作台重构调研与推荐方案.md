# 微信聊天档案工作台：调研与推荐方案

调研日期：2026-10-18。交付性质：产品与架构决策方案，尚未实施业务重构。

**推荐：建设可随包交付运行环境的 Windows 本地桌面工作台。使用 React + TypeScript 实现界面，保留 FastAPI、SQLite 与现有 Python 处理链路，以 pywebview 的 EdgeChromium 窗口作为默认载体，优先交付内置 Python 的便携文件夹包。会话浏览、正文检索、上下文阅读和分析共享当前探索条件；设置与任务按需打开。**

判断依据是当前项目的 Windows 本地用途、本地处理能力，以及用户明确提出的日后方便打包与开箱即用要求。桌面化提供目录选择、结果保存和生命周期；运行环境随包交付消除终端用户配置开发环境的需要；工作台提供查找、阅读、分析和输出。这三部分在同一架构下设计。

文中“已验证”指本轮源码、合成数据界面或官方文档直接支持；“推断”指设计与工程判断；“假设”指当前尚未获得用户行为证据的前提。

**2. 产品目标与主要使用路径**

[已确认] 用户要求日后方便打包为开箱即用状态。以 Windows 单机为首个交付目标，终端用户无需预装 Python、Conda、Node 或配置解释器路径。[假设] 首个发布形式采用可写目录中的便携文件夹包；安装向导、自动更新和多人协作尚不是已确定需求。

优先服务三种任务：

- 找回一件事：找到会话或正文，定位具体消息，读懂前后文。
- 复盘一个时段：明确会话与日期，查看消息分布，点击异常高峰或发送者返回原文。
- 输出一份记录：确认会话、时段与是否只含命中，导出有出处的材料。

“现代”体现为操作连贯、响应清楚、布局稳定；“高信息量”体现为可比较、可筛选、有层次；“可分析”体现为图表和消息使用一致条件，并能相互定位。

**3. 方案竞争与最终取舍**

| 候选方向 | 有价值的部分 | 不采用为主结构的原因 | 最终保留 |
|---|---|---|---|
| 模仿微信的聊天阅读器 | 熟悉的会话与正文组织 | 不擅长跨会话比较、筛选与精确输出 | 会话列表和持续阅读 |
| 数据库式密集表格 | 批量管理、排序和字段比较 | 长文本阅读弱，首次使用容易像数据库管理工具 | 可切换的档案表格模式 |
| BI 仪表盘首页 | 快速理解范围与时间分布 | 首屏数字缺少问题上下文，易脱离原文 | 当前范围内的分析视图 |
| 项目/材料研究系统 | 长期专题、摘录与笔记 | 引入工作集、材料篮等新集合，扩大首版学习成本 | 后续按真实需求增加保存视图 |
| AI 知识库与关系图谱 | 语义发现与辅助总结 | 基础检索和证据定位尚未完善，推断也需额外验证 | 待检索闭环稳定后评估 |
| 档案探索工作台 | 让查找、阅读、分析、导出接续发生 | 需要少量新查询接口，超过纯样式修改 | 采用为产品主方向 |

[推断] 最佳组合是“会话阅读的直接性 + 数据工具的筛选与比较 + 明确的处理与输出状态”。这些能力围绕当前任务出现，不同时占满首页。

第二轮审查修改了两项最初建议：不把档案、搜索、分析拆成三个独立导航页；不默认使用永久三栏加固定左导航。两者都会在常见笔记本分辨率上增加切换或挤压阅读空间。

**4. 推荐信息架构与界面行为**

应用只有一个主要工作区“档案探索”。账号位于顶部；任务状态、数据设置为辅助入口。首次尚无档案时展示引导，完成后默认恢复上次打开的会话及阅读位置。

探索区有两种主视图：

- 阅读：会话或检索结果列表与消息上下文并排；支持日期定位和明确的命中标识。
- 分析：在相同探索条件下，以时间分布和分类统计替换主要阅读区域；点击图表切回对应消息。

会话搜索和消息搜索使用明确的切换标签。前者沿用备注、昵称、alias、username 与已收录发送者关联；后者查询消息正文及可选成功转写。输入“报销”不应让人猜测系统正在搜索联系人还是正文。

1366×768 的设计起点：顶部约 48px，左侧会话区约 320px，其余给主阅读区；详情采用抽屉。默认没有永久右栏，没有首页大指标卡。阅读标题和筛选摘要固定，正文独立滚动，会话列表保留原滚动位置。

较宽屏幕可以按需固定约 300px 的详情或分析面板；窄窗口则按列表与正文两层切换。宽度以原型检验为准，上述数值是设计起点。

会话区提供“列表 / 表格”切换：列表适合阅读；表格适合比较名称、类型、归档状态、最近消息、数量和关注状态。待导入显示“待导入”，不显示为零消息。完整 username 保留在详情与同名区分中。

批量操作只在勾选后出现，显示“已选 N，当前筛选外 M”，并可展开完整选择清单。点击一行只是阅读；复选框决定批量操作；关注表示后续维护范围。三个状态分别表达。

首次准备分为目录与账号、通讯录与身份、选择维护范围三个阶段。加密库需要的密钥步骤按条件出现；明文库跳过。配置完成后仍可从数据设置修改，保存账号的归属确认规则继续保留。

任务状态在顶部显示阶段，点击打开抽屉，展示实际范围、结果、失败原因和可执行下一步。没有总量的阶段只展示阶段状态。首版支持当前/最近任务，不暗示已有历史队列、取消和暂停。

**5. 视觉方向：安静、密集、偏文档阅读**

采用浅色中性底、明确分区与细分隔线。绿色只表达当前主操作和选中关系，警告与失败使用各自语义色。圆角用于输入、按钮与浮层，正文和表格依靠对齐与间距建立结构。

建议初始 tokens：背景 `#F5F7F8`、内容面 `#FFFFFF`、正文 `#202A33`、次要文字 `#586773`、分隔 `#D8E0E5`、主操作 `#22664F`。这是待原型验证的设计选择，不是已验证的对比度结果。

字体使用本机中文 UI 字体，例如 Microsoft YaHei UI，配 Segoe UI；正文约 15px，表格约 13–14px，说明约 12–13px。默认会话行约 56px，表格紧凑行约 40–44px；允许舒适/紧凑密度切换。消息长文保留自然段，时间与发送者形成稳定边界。

分析界面优先使用可点击的时间柱形图和水平分布条。默认不展示词云、关系网络与装饰性仪表盘。图表提供同条件数字或表格入口，使信息不只依赖颜色。

键盘重点支持会话上下移动、打开、返回、搜索和日期定位；焦点可见，抽屉关闭后回到原控件。具体快捷键避免覆盖文本编辑和系统常用行为，原型阶段验证。

**6. “可分析”的最小完整版本**

第一条验收路径：打开项目群，输入“报销”，得到命中片段与“每日命中消息数”；选择某一天，点开一条命中，查看前后文，再导出当前条件的命中消息。

首个分析闭环默认作用于当前已归档会话。多会话范围随后复用相同查询语义扩展，不先引入工作集系统。界面重构里程碑可以先保留现有检索能力交付，但只有完成正文搜索、定位、下钻与结果导出后，才称为可分析版本。

这条路径至少新增三个后端能力：

1. 消息查询：会话、消息时段和关键词，返回分页结果、命中总数与日分布；成功转写的检索来源要显式标记。
2. 消息定位：以账号、会话和稳定 message_id 返回前后文，并延续当前稳定排序语义。
3. 命中导出：使用与搜索相同的条件，输出实际命中正文和会话、发送者、时间及生成时的筛选说明。

现有每次 5 条预览应调整为合理的按需批量读取，例如以 50 条作为初始页长。首版可保留有界分页；深页变慢时改用稳定多列排序键的游标。SQLite 官方展示了滚动窗口中使用行值比较减少大 OFFSET 成本的方式。[官方说明](https://www.sqlite.org/rowvalue.html#scrolling_window_queries)

搜索、搜索计数、日桶和命中导出复用同一条件构造逻辑。不要把全产品的配置、选择与任务强塞成一个巨型状态对象。

进一步的事实分析按需求扩展：已归档消息数、活跃天数、消息类型分布、已收录发送者分布、语音转写状态。每个统计项点击后都能查看构成它的消息。Datasette 的 facets 提供了“汇总同时是筛选入口”的成熟参照，可借鉴交互原则，不必引入整套服务。[官方文档](https://docs.datasette.io/en/stable/facets.html)

指标口径必须明确：

| 指标 | 定义 |
|---|---|
| 已归档消息数 | 当前范围内去重后的归档消息行数 |
| 活跃天数 | 本机指定时区下，至少存在一条范围消息的自然日数 |
| 已收录发送者数 | 范围内消息出现的发送者身份数，未知身份单列 |
| 每日命中消息数 | 当前正文检索条件下，每日匹配消息数 |
| 转写覆盖率 | 成功转写语音数 / 范围内语音数，同时列出未请求、缺失与失败 |

收发方向根据稳定身份计算；无法确认时显示未知，不能把显示名“我”当成身份依据。消息类型按当前解析粒度展示，不能把混合的链接/文件类型画成精确的两类。

**7. 范围和一致性规则**

为避免操作含义漂移，保留两种已有范围，并明确新增查询范围：

- 会话条件决定会话列表显示哪些对象，包含现有活动时段/完整起止筛选；它不会悄悄限制导出正文。
- 阅读消息时段决定当前聊天阅读和原有整段导出的日期。
- 在阅读时段上进入“搜索消息”，关键词构成搜索条件；日图的刷选进一步缩小当前消息范围。清除搜索恢复普通阅读。

搜索和分析共享当前消息查询条件；列表日期属于会话筛选，不提升为含糊的全局日期。这样既让分析连贯，也保留现有行为的作用域。

导出面板显式区分“导出消息时段内全部记录”和“仅导出当前搜索命中”。展开的上下文默认不计入命中数，也不自动进入命中导出。列表高亮、搜索命中和批量勾选使用不同表现。

导入与语音转写继续按会话集合执行，消息搜索和日期不缩小维护范围。操作面板写明“处理所选会话的全部历史”。后续如果支持按消息转写，应作为单独能力设计。

一次搜索的列表、总数和日桶来自同一只读快照。维护发布新数据后保留条件并刷新整组结果，给出简短更新提示。导出以执行时已发布档案重新查询，在文件中记录实际数量、条件和生成时间；不用为浏览会话保留长事务或建设版本系统。

账号最近成功更新不代表每个会话同样新。首版显示准确的账号更新时间；若需要每会话核对时间，补齐记录后再显示，不从首末消息时间推断。

**8. 架构与桌面形态的选择**

推荐的层次：React/TypeScript 界面负责探索与呈现，FastAPI 负责现有业务及查询，SQLite 继续作为档案源，pywebview 提供窗口与少量原生动作。基础 Python 随应用交付，可选 ASR 使用独立随包运行时；现有机器的 Python 环境仅作为开发或高级用户选项。

| 载体 | 结论 | 原因 |
|---|---|---|
| 浏览器 | 保留开发及诊断入口 | 复用成本最低，但路径、保存、服务退出体验仍需管理 |
| pywebview + EdgeChromium | 默认桌面方案，前置验证随包依赖 | 沿用 Python，承接目录、保存和窗口操作；Python、.NET 与 WebView2 交付需一起验证 |
| Tauri 2 + Python sidecar | 有明确发行收益时重新评估 | 支持 Python sidecar，但引入 Rust、侧进程和打包协调；基础开箱即用本身不足以要求切换 |
| Electron + Python | 当前不选 | 尚无需要 Node/Electron 特定能力或固定 Chromium 的需求 |
| PySide/Qt 原生重写 | 当前不选 | 有部署工具；主要代价在于 UI 重写，而非“Qt 不能现代化” |

pywebview 官方支持窗口、JavaScript/Python 桥及关闭事件；GUI 循环阻塞，FastAPI 应独立运行并由启动器管理。[Usage](https://pywebview.flowrl.com/guide/usage.html)

Windows 必须显式使用 `edgechromium` 并检查 WebView2，不能让缺失环境回退到已弃用 MSHTML。[Web engine](https://pywebview.flowrl.com/guide/web_engine.html)

原生桥只做选择目录、保存/打开结果和退出。业务继续走 FastAPI；前端由该服务同源提供，保持当前请求来源约束。原生保存成功必须以实际写入完成为准，不能仅把浏览器下载文案改成“已保存”。

首版桌面生命周期明确为：无任务时退出关闭窗口及自身启动的服务；维护中关闭时提示任务未完成并保持窗口，用户可最小化继续。暂不引入托盘驻留、后台服务或任务暂停。明确退出后如何处理运行任务，是桌面版的验收项。

技术建议：Vite 产出静态前端；React + TypeScript 管理多区域状态；Ant Design 提供表格、筛选、抽屉与表单等基础控件，自定义工作台布局；TanStack Query 管理服务查询、缓存和失效；图表用 ECharts 按需加载。消息列表确需虚拟化时再引入 TanStack Virtual，不能用虚拟渲染替代后端分页。

这些选择分别有官方能力依据：[Ant Design Table](https://ant.design/components/table/)、[TanStack Query](https://tanstack.com/query/latest/docs/framework/react/overview)、[TanStack Virtual](https://tanstack.com/virtual/latest/docs/introduction)、[ECharts 事件](https://echarts.apache.org/handbook/en/concepts/event/)。它们是适配本项目的推荐，尚未在本项目安装验证。前端不需要 SSR 或独立 Node 生产服务。

Tauri 的重新评估条件是标准安装、自动更新或系统集成需求带来的明确收益，而不是“用户电脑没有 Python”。内置 Python 或冻结后的 pywebview 应用同样可以无需预装 Python。Tauri 官方支持将 Python CLI/API 经打包后作为 sidecar；它不会自动消除 Python、语音工具和模型的交付成本。[官方文档](https://v2.tauri.app/develop/sidecar/)

重构时即需处理两处打包边界：`maintenance.py:189` 用 `sys.executable` 启动脚本，冻结后它不再等同普通 Python 解释器；`web/app.py:24` 把数据写在代码目录旁，需要明确的可写持久目录。前者见 [PyInstaller 运行信息](https://pyinstaller.org/en/stable/runtime-information.html)。便携版优先显式使用包内 Python 启动工具与 worker，不依赖入口是否冻结；路径和数据分离从重构开始落实。

**8.1 开箱即用的发布约束与界面影响**

已读取关联聊天[《调研项目开箱即用打包方案》](thread://01a14a91-4d9a-7270-baa6-4777bde04d1b?hostId=local)，其推荐为内置 Python 的便携 ZIP、独立语音完整包；该聊天没有进行试构建。其“保留浏览器”适用于当前界面的最低改动分发路线；本方案需要重构工作台，因此采用相同的运行环境交付方式，并增加薄桌面窗口。两者的打包原则兼容。

首个交付目标：基础版解压到可写目录即可双击进入档案引导，无需运行 pip、npm 或输入开发环境路径。完整语音版另带经验证的语音运行时、SILK 解码、FFmpeg 和本地模型，以 CPU 可运行为基线；GPU 为后续可选能力。基础版和完整语音版共享界面与业务代码。

Python 官方支持把嵌入式运行时作为应用的一部分交付；依赖应在构建阶段准备，不让用户首次运行安装。[Python 官方文档](https://docs.python.org/3/using/windows.html#the-embeddable-package) 具体 Python 版本和语音运行时形态需由依赖兼容验证确定，不直接复制本机 Conda 环境并宣称可移植。

建议发布目录的职责为：根目录放启动入口；`app/` 放应用与已构建的前端；`runtime/` 放基础运行时；完整版另有 `voice-runtime/` 与 `models/`；便携版根目录 `local_data/` 首次运行创建并在更新时保留；`licenses/` 放发布依赖许可。前端在构建机生成静态文件，目标电脑不运行 Vite 或 Node。

实现时落实以下规则：

- 程序资源、用户数据、模型与日志路径显式区分，均不依赖当前工作目录或开发者机器绝对路径。便携版升级替换程序文件，保留档案；安装版如以后提供，再选择稳定用户数据位置。
- 密钥工具使用包内基础解释器，语音使用包内语音解释器。冻结启动器后也不拿启动器的 `sys.executable` 冒充 Python。
- pywebview 的 .NET 与 WebView2 前置依赖纳入发布准备和启动检查。联网安装包可引导补齐；若承诺完全离线，则带离线安装资源或经验证的运行时方案，不能假定所有目标 Windows 都已经具备。[pywebview 安装要求](https://pywebview.flowrl.com/guide/installation.html)、[WebView2 分发文档](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)
- 发布从明确的程序资源清单组装，不直接压缩工作目录；现有密钥、档案、解密库和导出文件不进入发布包。固定已验收的依赖版本。
- 发布目标首先是文件夹/ZIP。单 EXE 不是开箱即用的必要条件；若采用 PyInstaller，优先评估 onedir，并处理所有子进程和原生依赖。[pywebview 冻结文档](https://pywebview.flowrl.com/guide/freezing.html)

界面相应调整：启动先显示就绪与失败状态；首次引导只要求选择微信目录、确认账号和身份。基础版语音区显示“未包含语音组件”，提供添加完整组件包的路径；完整版自动发现随包模型。解释器路径、模型高级路径等放到高级设置，不要求普通用户填写。

完全离线、无需安装任何额外系统组件是比“无需 Python”更强的交付承诺，需单独验证。提取密钥仍可能需要当前微信已登录或适当权限；这些业务前提在相应操作中说明。

**9. 中文搜索与性能决策**

全文搜索是功能目标，FTS5 是可能的实现工具。默认 tokenizer 不等同中文分词；FTS5 trigram 的 MATCH 对不足三个 Unicode 字符的查询不命中。“报销”“地址”“合同”都是实际主路径，不能要求用户凑满三个字。[SQLite FTS5 官方文档](https://www.sqlite.org/fts5.html#tokenizers)

首版在当前会话与日期范围内实现正确的子串检索，验证两字中文、人名、数字、英文和转写。以项目支持规模进行合成数据测量；若范围内查询仍慢，再决定引入中文分词、二元索引或 FTS 路由。全库搜索另设明确性能验收，不将单会话体验外推为全库承诺。

新增索引必须覆盖导入新增、正文变更、消息标识合并及转写成功/失效这些真实路径；不只在首次导入建立。分析首期用 SQLite 查询，不预设需要 DuckDB、独立搜索服务或预聚合表。

会话量增大后，将当前 Python 整体加载与逐会话活动计数下推为可分页查询。是否加入虚拟列表、日聚合表或后台文件导出，由能复现的查询、渲染或内存瓶颈决定。

**10. 实施顺序与完成条件**

| 里程碑 | 范围 | 完成条件 |
|---|---|---|
| 0：最小交付验证 | 包内 Python、静态前端样例、pywebview/WebView2、工具子进程；语音单独探测 | 在没有开发环境的目标 Windows 上启动窗口并调用随包子进程；发现不兼容先调整交付组合 |
| A：工作台界面 | 分离首次引导；会话/表格与固定阅读区；批选操作条；任务和导出抽屉；改善消息页长 | 可从联系人找到关联群，阅读指定月份并导出，筛选、关注、选择语义正确 |
| B：最小分析闭环 | 单会话正文与成功转写搜索；命中上下文；每日命中图下钻；显式命中导出 | “报销”等两字查询可找到记录，图表计数可回查，导出范围准确 |
| C：完整桌面便携交付 | pywebview；目录与保存；服务生命周期；基础包与完整语音包；数据保留 | 无 Python/Node/Conda 的目标 Windows 可双击使用；中文/空格路径、重启及替换程序后档案可用；完整包离线转写可用 |
| D：有用的扩展 | 多会话搜索、类型/发送者下钻、保存视图、按规模优化 | 由实际反复使用场景和查询表现确定优先级 |

A 是可用的界面替换；0+A+B+C 是本方案建议的首个完整桌面工作台。0 在开发早期完成，C 完成交付验收，路径及运行时约束贯穿 A/B。分步验收，避免在一个改动中同时重写界面、解析器和归档事务。材料篮、AI、安装向导和自动更新后置；随包运行与数据保留属于首版要求。

后续验证只针对明确风险：

- 两字中文、转写命中与上下文：检测漏检和命中定位错误；失败则修改查询/定位实现。
- 同名联系人、待导入、隐藏选择与两类日期：检测会话身份和操作范围混淆；失败则修正状态与交互。
- 查询计数、日桶与导出：检测口径分叉；失败则共用查询条件并修复输出。
- 更新期间继续阅读与导出：检测现有事务发布语义被破坏；失败则修正读取与刷新时机。
- 合成规模档案：检测可支持范围内的查询、渲染或导出瓶颈；失败后才引入对应优化。
- 桌面就绪、目录与保存、运行中关闭：检测空窗口、路径或生命周期问题；失败则修正启动器与原生动作。
- 无开发环境的目标 Windows、离线语音和升级保留档案：检测遗漏的原生依赖、模型、绝对路径及数据目录错误；失败则修正发布内容与路径，不能用开发机运行通过代替。

**11. 限制、风险与改变推荐的条件**

现有项目已在实际使用，作为本次重构的功能基础。后续验证聚焦新增界面、检索分析和随包运行能力，以及重构是否保持现有行为。

最高优先风险是范围混淆、中文漏检、统计被误读为完整微信历史，以及窗口关闭中断任务。已有账号隔离、历史保留、事务发布和维护串行语义应继续作为基础。

开箱即用已是确定约束，pywebview 与内置 Python 的完整发布组合尚未试构建，因此载体推荐仍需里程碑 0 验证。若原生依赖无法在目标环境可靠交付，应先调整运行时或载体。明确要求自动更新等发行能力会提高 Tauri 的优先级；明确只用浏览器会取消桌面载体；明确需要跨会话研究会前移多会话检索；明确需要长期摘录材料会推动材料篮；真实规模测量才决定索引与导出优化。

下一步应先用最小交付验证确认包内运行时和桌面依赖，再制作采用该信息架构的可交互原型，覆盖“打开档案—检索正文—查看上下文—下钻—核对导出”一条路径；后续业务实现持续使用可随包运行的路径与进程入口。
